Ownership and security

The phone talks to Postgres directly through Supabase's API, so the database itself decides who sees what. There is no server of ours in between.

  • Row level security on all 15 tablesOne policy shape everywhere: user_id = auth.uid() for reading (USING) and for writing (WITH CHECK), so a row can't be handed to someone else on update.
  • Owner-scoped foreign keysPostgres checks foreign keys with RLS switched off. Children reference parents by (id, user_id), so a bag can only point at a coffee with the same owner.
  • Views run as the callerAll four views use security_invoker = on; without it a view would quietly bypass RLS on the tables underneath.
  • One folder per user in StoragePhotos live at <user_id>/<import_id>/<n>.jpg in a private bucket (10 MB, JPEG/PNG/WebP). Storage policies only allow your own folder.

Tables

Columns that carry meaning, with their types and the rules the database enforces.

Every table also has id uuid (primary key, except the two link tables), user_id uuid → auth.users and created_at timestamptz. Most have updated_at, kept current by a trigger. profiles is keyed by the auth user's own id and holds display_name and default_currency (default EUR).

coffee_varieties

Which cultivars are in a coffee. A single origin is one row; a blend is several.

  • coffee_id→ coffees

How stock is counted

Like an accounting ledger: movements are rows, and the balance is a sum.

You never write stock yourself. Adding a bag makes a trigger write a purchase row for its label weight. Logging a brew writes a matching negative brew row, and editing or deleting the brew updates or removes that row, so the two can't drift apart.

Spills, dialing-in shots and coffee you give away are waste and gift. Weighing the bag and finding it differs is an adjustment.

Fixing a typo in a bag's weight rewrites its purchase row instead of adding a correction, because the typo was never a real-world event.

Keeping the history means questions like "how fast do I finish a bag?" can be answered later, and a half-failed write can't silently corrupt a stored balance.

Import lifecycle

An import is a small pipeline run. Its status can only move along these arrows; a trigger rejects anything else.

  • Bronze · raw import_jobs.raw_payload

    The page text, JSON-LD and meta tags as fetched, or the list of photos read. Kept so a better prompt can be re-run without fetching again.

  • Silver · extracted import_jobs.extracted

    Every field as { value, confidence }, plus warnings and lineage: schema and prompt version, model, token usage.

  • Gold · confirmed coffees + bags

    Typed rows written by confirm_import after you review, in one transaction: roaster, coffee, varieties and bag, or nothing.
